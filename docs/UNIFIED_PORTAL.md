# 统一门户与 Go 版 QMS 服务

## 服务结构

| 服务 | 默认地址 | 作用 |
| --- | --- | --- |
| 统一门户与首末检 API | `http://127.0.0.1:8090/portal/` | 统一登录、系统入口、跨系统查看授权、首末检业务 |
| QMS Go 服务 | `http://127.0.0.1:8081/` | 质量管理、环境设备、历史查询和导出 |
| PC 首末检 | `http://127.0.0.1:8090/pc/` | 首末检 PC 管理与填报 |
| PDA 首末检 | `http://127.0.0.1:8090/pda/` | 首末检移动填报 |

门户、首末检和 QMS Go 服务共用 PostgreSQL 用户表和 JWT。QMS 静态前端完整保存在项目内的 `qms-web/`，由 Go 服务直接提供，不依赖旧 Java 项目目录。

## 统一账号与登录

门户和子系统使用同一条 `users` 账号记录，账号、密码、启停状态和角色统一维护。使用账号密码登录门户后，进入已授权的首末检 PC、PDA 或 QMS 时直接复用当前登录，不需要再次输入账号密码。PC/PDA 即使打开登录页，也会先检查已有会话并直接进入工作台。

登录通过同一主机上的 HttpOnly Cookie 在不同端口间共享。访问时请统一使用同一个主机名或 IP，例如都使用 `192.168.31.34`，或在本机都使用 `localhost`；不要在门户使用 `localhost` 后又手工把子系统地址改成 IP。门户系统入口会保留当前访问主机。

子系统继续检查系统查看授权、角色允许的客户端和功能权限。没有权限时显示授权提示，不要求反复登录。PDA 单独按工号登录的会话不能访问 PC 管理接口；从门户登录的账号需要具备 PC 登录权限才能进入管理端。

首末检系统默认打开 PC 管理端；角色仅允许 PDA 时，门户自动打开 PDA 工作台。

在任一入口退出登录会清除浏览器中的共享 Cookie，其他入口在下次请求或页面导航时需要重新登录。

## 首末检账号的默认入口

首末检管理端手工创建、Excel 批量导入账号时，账号记录与首末检系统入口授权在同一数据库事务中保存。默认入口只用于进入首末检，PC／PDA 登录及系统内功能仍按原有角色权限校验；其他系统继续在门户单独授权。

已有数据库升级时，迁移 `000015_existing_user_inspection_access` 会补齐门户接入后遗漏的首末检入口。已有入口记录、管理员曾明确维护过的系统授权不覆盖。账号或部门停用状态保持不变。该数据修复回滚时不自动撤销入口，撤销请在门户系统权限中明确保存。

## 两层权限

1. 门户层：`portal_system_access` 只决定账号能否查看某个系统。
2. 系统层：统一使用现有 RBAC 角色权限决定进入系统后能查看或执行哪些功能。QMS 已新增 `qms.view`、`qms.history`、`qms.export`。

超级管理员仍由 `users` 表上的唯一性数据库触发器约束，只允许一个启用的全局超级管理员。门户刷新所有系统权限时不会修改该角色。

## 新增系统

系统接入由 `portal_systems` 注册表驱动，不需要修改门户首页逻辑：

1. 在 `portal_systems` 新增记录，填写系统编码、名称、入口路径、端口、健康检查和排序。
2. 在目标服务中验证统一 JWT，并查询 `portal_system_access` 确认账号有该系统查看权限。
3. 目标服务继续维护自己的内部权限码和角色关系。
4. 门户的“系统注册”和“系统权限”页面会自动显示新记录。

如果后续系统数量增加，可以将入口配置扩展为网关 URL、图标资源或分级目录；当前表结构已经为此保留独立字段。

## 启动

```text
复制 server/.env.example 为 server/.env，填写数据库、JWT 和 IoT 凭据
powershell -ExecutionPolicy Bypass -File scripts\migrate.ps1 up
powershell -ExecutionPolicy Bypass -File scripts\dev-all.ps1
```

已有数据库升级时也必须执行上述迁移命令。迁移 `000014_bearing_entry_port` 会把首末检注册入口中遗留的 `8080` 修正为 `8090`，其他自定义端口保持原值。修改初始迁移文件不会更新已经建好的数据库；本地 `dev-all.ps1` 启动时会自动执行新增迁移。

升级时保留已有角色授权。需要使用 QMS 的旧账号，请通过门户的「系统权限」授予系统访问，再通过「子系统权限」配置其角色需要的 QMS 功能。QMS 使用通过门户或 PC 验证密码后的会话。

门户在浏览器返回恢复旧页面时重新读取会话和入口配置，点击系统卡片前也会更新入口。退出登录会清理当前页面状态，并丢弃退出前尚未结束的会话请求结果。若浏览器当前停留在旧的 `:8080/pc/` 或 `:8080/portal/` 地址，请重新打开 `:5175/portal/` 开发入口，或 `:8090/portal/` 服务入口。

单独构建：

```text
npm.cmd run build
cd server
go test ./...
go build -buildvcs=false -o bin\bearing-inspection.exe ./cmd/api
go build -buildvcs=false -o bin\qms.exe ./cmd/qms
```

## 设备历史查询

设备历史页默认查询最近 7 天；近 1/3/7/30 天及自定义范围均读取该范围内全部记录，不再提供总条数选择。前端按时间游标分批读取，显示读取进度并支持取消；读取失败不会将部分结果标为完整。每批大小仅控制单次请求量，不限制总量。主表与 SPC 明细均分页显示，只渲染当前页，大结果不做深层响应式代理。原始报文和 CSV 导出默认也完整读取所选范围。

当前范围为空时，页面会读取设备最近一次上报时间，并提供“查询最近上报记录”按钮，明确切换到最近上报前一天至后一分钟的自定义范围。停机或长时间未上报的设备不会显示为接口故障。

SPC 报文与普通运转字段同时存在时，两类数据均参与历史解析，质量项可在主表和 SPC 明细中查看、导出。更换设备时，旧查询的延迟响应不会覆盖当前结果。

异常数量固定显示在历史结果标题栏，即使为 0 或当前未选栏目也显示；两个页签均按当前选择计算。页面脚本使用内容版本号，避免浏览器缓存旧脚本造成统计空白。

异常数量按原始采集时间戳（毫秒）去重：同一采集时间任意多个已勾选栏目不合格，仅计 1 条；取消某栏目后，该栏目不再参与异常统计。若同一时间仍有其他已选栏目不合格，仍计 1 条。统计覆盖整个查询范围，不限当前页；“只看异常”使用相同判定集合。SPC 明细的异常统计同样仅统计已选栏目、按时间去重；原始明细仍完整保留。

### 设备改号（旧设备条目数据合并）

设备在 ThingsBoard 中改号时，改号前的历史遥测仍保留在旧设备条目下。QMS 通过 `server/device-aliases.json` 配置“当前设备 → 改号前设备条目 + 切换时间”，历史查询、原始报文和导出会把旧条目在切换时间之前的数据并入当前设备，页面按当前编号即可看到连续历史。

```json
{
  "aliases": [
    {
      "deviceId": "当前设备 ID",
      "legacyDeviceId": "改号前设备条目 ID",
      "switchAt": "2026-11-02T13:33:05.787+08:00"
    }
  ]
}
```

- 配置文件路径由 `QMS_DEVICE_ALIASES` 指定，默认 `server/device-aliases.json`；文件不存在时服务正常启动，仅不合并旧数据。
- 修改配置后需要重启 QMS 服务生效。
- 合并规则：时间戳早于 `switchAt` 的旧条目数据并入当前设备；同一字段同一时间戳两边都有值时保留当前设备的值。
